TLA+ primer

You need six ideas to read the specifications on this site.

1. A state is a value for every variable

Each module declares its variables with VARIABLES. A state gives each variable one value. For example, RactorPorts has portOpen = <<TRUE, TRUE, TRUE>> and queue = <<0, 0, 0>> in its initial state. A tuple <<a, b, c>> is a function from 1..3, so queue[2] is the number of messages on port 2.

2. An action relates one state to the next

An action is a formula over unprimed variables (the state before) and primed variables (the state after). It is enabled when it can be true. This is Send from RactorPorts:

Send(c, p) ==
  /\ Alive(c)
  /\ portOpen[p] => queue[p] < QueueBound
  /\ IF portOpen[p]
       THEN /\ queue' = [queue EXCEPT ![p] = @ + 1]
            /\ step' = Step("Send", <<c, p>>, "ok")
       ELSE /\ UNCHANGED queue
            /\ step' = Step("Send", <<c, p>>, "Ractor::ClosedError")
  /\ UNCHANGED <<aspect, workerAlive, portOpen>>

Read it as: Ractor c sends to port p while c is alive. If the port is open, its queue grows by one and the call returns. If the port is closed, nothing changes and the call raises Ractor::ClosedError.

3. A specification is Init and Next

Spec == Init /\ [][Next]_vars says: the first state satisfies Init, and every step satisfies Next or leaves vars unchanged. Next is a disjunction of every action with every argument, so it lists every call a program can make.

RactorPool adds WF_vars(Next) (weak fairness). It says that a step that stays enabled is eventually taken. Without it, "the pool eventually finishes" cannot hold, because a behavior could stop.

4. One API call is one action

The API modules record the last call in the variable step as [op |-> "Send", args |-> <<1, 2>>, outcome |-> "ok"]. An invalid call is an action too: it sets step to the exception class and leaves the rest of the state alone. So a specification states what a call returns, what it raises, and what a program sees after it rescues the error.

RactorPorts and RactorTermination add a field value. It names what an ok call returns, for example "P2" when Ractor.select returns [P2, :msg], or "exited" for the token [ractor, :exited]. The replay compares that value too.

A blocking call such as Ractor::Port#receive on an empty open port has no result. The models enable it only when it returns at once. The timeout: 0 variants (Poll, SelectPoll) document the non-blocking contract instead.

5. Guarantees are invariants and temporal properties

  • An invariant is a state formula that holds in every reachable state, for example TerminatedWorkerPortsClosed.
  • A step property [][A]_vars holds for every step, for example ClosedStaysClosed: a closed port is closed in the next state too.
  • A liveness property uses <> (eventually) or ~> (leads to), for example EventuallyCompleted in RactorPool.

6. TLC checks a bounded model exhaustively

TLC enumerates every reachable state from Init through Next and checks every guarantee in every state. The models are small on purpose: two or three Ractors, a queue bound of one, one object in flight. A rule that holds for every combination at this size is a precise statement of the API. It is not a proof for every program size.

Some modules choose an aspect in Init, for example "exit" or "abort" in RactorTermination. TLC explores each aspect as a separate subgraph, so one module covers one topic with small state.

How this site uses the state graph

  • Distinct API states: TLC states merged when they differ only in step.
  • Transition: one (state, call) pair. The builder checks that each pair has exactly one outcome and one next state.
  • Lifecycle diagram: the graph projected onto one variable. Edges list the calls that move it.
  • Shortest witness: the shortest call sequence from Init that reaches a given outcome, found by breadth-first search.
  • Replay: a call sequence run in a fresh CRuby process, with every outcome and observable compared to the model. The paths cover every transition.
